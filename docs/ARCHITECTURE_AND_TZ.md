# Описание программы и ТЗ на изменения

Документ содержит: **А** — описание текущей программы (пайплайн и архитектура); **Б** — техническое задание на изменения (пункты 1–7, в т.ч. сохранение контекста чата) и предложения по улучшению (п. Б.8).

## Часть А. Текущее состояние программы

### А.1. Обзор

**Paynet RAG Chatbot** — FastAPI-приложение, реализующее чат-бота для колл-центра Paynet. Бот:

- Отвечает на запросы на **русском** и **узбекском** (латиница) на основе базы знаний (PDF).
- Использует **RAG**: поиск релевантных фрагментов в БЗ → генерация ответа через OpenAI.
- Определяет язык (ru/uz), нормализует синонимы, классифицирует запросы, анонимизирует PII, поддерживает эскалацию на оператора.
- Логирует взаимодействия в PostgreSQL, кэширует эмбеддинги и детекцию языка в Redis, отдаёт метрики в Prometheus.

Запуск: один процесс `uvicorn bot9b:app` (порт 8000), отдельно — метрики на 8001.

### А.2. Пайплайн обработки сообщения (текущий)

Последовательность от входа запроса до ответа:

1. **Вход**: `POST /process_message` с `chat_id` и `message`.
2. **Валидация**: проверка наличия `chat_id` и `message` → 400 при отсутствии.
3. **Определение языка**: `detect_language_openai(message, chat_id, redis)`:
   - контекст запроса (ContextVar);
   - при неопределённом тексте — `last_language` из Redis или дефолт `uz`;
   - кэш Redis по хэшу текста;
   - при отсутствии в кэше — вызов OpenAI (gpt-4o-mini) для ru/uz.
4. **Анонимизация**: `anonymize_message(message)` — маскирование телефонов, паспортов, карт, PINFL, email по regex.
5. **Проверка PII-only**: если после анонимизации текст пустой или только "***" → ответ «задайте вопрос без личных данных», без RAG.
6. **Redis (сессия)**:
   - обновление `chat:*:seen`, `chat:*:active`, `chat:*:start_time`;
   - добавление сообщения в `chat:*:history` (обрезание до `MAX_HISTORY_SIZE`);
   - чтение последнего эмбеддинга и счётчика повторов.
7. **Эмбеддинг запроса**: `get_embedding(anonymized_message, redis)` — OpenAI text-embedding-ada-002, кэш в Redis.
8. **Детекция повтора**: сравнение с последним эмбеддингом (cosine similarity > 0.9) → увеличение счётчика; иначе сброс на 1.
9. **Классификация**: `classify_query(message, language, redis)` — сначала локальные ключевые слова (CATEGORIES), при отсутствии совпадения — OpenAI; результат кэшируется.
10. **Эскалация**:
    - если в сообщении есть ключевые слова оператора или счётчик повторов ≥ 3 → увеличение `escalation_count`;
    - при `escalation_count >= 3` → ответ «высокая нагрузка, звоните»;
    - иначе → ответ «передаём оператору», логирование, очистка сессии, возврат.
11. **Поиск контекста** (если не эскалация):
    - для «неопределённых» текстов контекст не ищется;
    - иначе: `find_relevant_context(query, query_embedding, vector_store, knowledge_base, language, top_k=3)`:
      - нормализация синонимов по языку;
      - FAISS: `index.search([query_embedding], 3)`, отбор по расстоянию < 0.9;
      - возврат списка чанков.
12. **Генерация ответа**: `generate_response(context, query, history, language)`:
    - язык **всегда** из шага 3 (передачи языка извне нет);
    - промпт зависит от языка (uz — латиница, ru — кириллица);
    - вызов OpenAI (gpt-4.1-mini), постобработка для uz (замена кириллических букв узбекского на латиницу).
13. **Логирование**: `log_interaction(chat_id, message, response, classification, tokens, escalation)` → INSERT в PostgreSQL `interactions`.
14. **Выход**: `MessageResponse(status, chat_id, response, classification, escalation, history)`.

Дополнительно: фоновая задача `cleanup_inactive_sessions` раз в 60 с сбрасывает сессии по таймауту (1 час) и обновляет метрику активных чатов.

### А.3. Архитектура (текущая)

**Компоненты:**

| Компонент | Назначение |
|-----------|------------|
| **FastAPI (bot9b)** | Единственная точка входа: эндпоинты, lifespan, вся бизнес-логика в одном файле. |
| **PostgreSQL** | Хранение `interactions` (chat_id, message, response, classification, tokens, escalation, timestamp). |
| **Redis** | Кэш эмбеддингов, кэш детекции языка, `last_language` по чату, история сообщений, счётчики повторов и эскалаций, флаги сессии. |
| **FAISS** | Векторный индекс в памяти: один `IndexFlatL2` размерности 1536; чанки хранятся в списке `knowledge_base`. Индекс и чанки загружаются при старте из `faiss_index.bin` и `knowledge_base.json` при совпадении хэша PDF в `kb_hash.json`. |
| **OpenAI** | Эмбеддинги (text-embedding-ada-002), детекция языка (gpt-4o-mini), классификация (gpt-4o-mini при fallback), генерация ответа (gpt-4.1-mini). |
| **Prometheus** | Метрики (запросы, латентность, эскалации, сессии, классификации, синонимы, детекция языка) на порту 8001. |
| **analyzer.py** | Отдельный скрипт: читает `interactions`, классифицирует сессии и считает QC (Q-Bot Index), пишет в `session_analytics_1`. Не входит в пайплайн бота. |

**Загрузка базы знаний (текущая):**

- При старте приложения в `lifespan` вызывается `load_knowledge_base()`:
  - читается `KB.pdf` из корня проекта;
  - считается MD5-хэш; при совпадении с `kb_hash.json` загружаются кэш FAISS и `knowledge_base.json`;
  - иначе: из PDF извлекается текст (pdfplumber), применяется **enhanced_text_chunking** (см. ниже), для каждого чанка — эмбеддинг (с семафором), строится FAISS-индекс, всё сохраняется в файлы.
- **Чанкинг**: разбиение по предложениям (`smart_sentence_split`) с учётом аббревиатур, затем сбор в чанки фиксированного размера (800 символов, overlap 100). **Семантический чанкинг не используется.**

**Поток данных (упрощённо):**

```
Клиент → POST /process_message
    → detect_language → anonymize → Redis (session) → embedding → classify
    → [escalation?] → find_relevant_context (FAISS) → generate_response (OpenAI)
    → log_interaction (PostgreSQL) → Response
```

**Структура кода:** один файл `bot9b.py` (~920 строк): константы, модели Pydantic, Redis-обёртки, синонимы, детекция языка, чанкинг, загрузка/сохранение БЗ, эмбеддинги, анонимизация, классификация, поиск контекста, логирование, очистка сессий, lifespan, эндпоинты.

## Часть Б. Техническое задание на изменения

### Б.1. Замена векторной базы на Qdrant + BM25 + лёгкий реранкер (uz/ru)

**Цель:** уйти от FAISS и только векторного поиска; использовать гибридный поиск (векторный + BM25) и реранкер, поддерживающий узбекский и русский.

**Требования:**

1. **Qdrant**
   - Хранить эмбеддинги чанков в коллекции Qdrant (размерность — по выбранной модели эмбеддингов, например 1024 для BGE-M3 или оставить 1536 при сохранении OpenAI).
   - Поиск: векторный поиск по запросу (top_k достаточно большой, например 20–50) для последующего реранкинга.
   - Имя коллекции/alias: по ТЗ из `KB_MANAGEMENT_FEATURE.md` — коллекция вида `kb_v1_{timestamp}`, alias `kb_current` для бесшовной переиндексации.

2. **BM25**
   - In-memory или внешний индекс BM25 по тем же текстам чанков (токенизация с поддержкой uz/ru: пробелы, при необходимости стемминг/нормализация).
   - По запросу возвращать top-N кандидатов по BM25.
   - Индекс пересобирается при каждой переиндексации БЗ (после обновления чанков).

3. **Гибрид**
   - Объединение кандидатов из Qdrant и BM25 (например, по doc_id), устранение дубликатов.
   - Передача объединённого списка кандидатов в реранкер.

4. **Реранкер**
   - Лёгкая модель, понимающая узбекский и русский (например, cross-encoder с поддержкой multilingual или специализированный reranker для uz/ru).
   - Вход: пары (запрос, чанк); выход: скор. Отбор топ-k после реранкинга (например, 3–5) для передачи в `generate_response`.
   - Требование: не тяжёлый (приемлемая задержка в пайплайне, например < 500 ms на запрос).

**Действия:** выбор и интеграция Qdrant (Docker/облако), выбор библиотеки BM25 (например rank_bm25), выбор и интеграция реранкера (например BGE reranker, Cohere rerank или лёгкий open-source multilingual), реализация единой функции поиска (vector + BM25 → merge → rerank → top_k), замена вызова `find_relevant_context` на новый поиск, обновление индексации в ТЗ п. Б.4.

### Б.2. Семантический чанкинг файла

**Цель:** заменить разбиение по фиксированному размеру (и предложениям) на семантическое разбиение, чтобы границы чанков совпадали с смысловыми блоками.

**Требования:**

1. Убрать использование только `enhanced_text_chunking` (sentence-based, chunk_size=800, overlap=100) при построении БЗ.
2. Ввести **семантический чанкинг**:
   - Вариант А: разбиение по параграфам/заголовкам (если PDF даёт структуру через pdfplumber).
   - Вариант Б: использование модели для определения границ (например, по эмбеддингам предложений и порогу схожести соседей).
   - Вариант В: готовые библиотеки (например, semantic chunking по смене темы или по embedding similarity).
3. Ограничения: максимальный размер чанка для эмбеддингов (лимит модели) и разумный минимум; при необходимости — мягкий overlap между соседними чанками.
4. Сохранить совместимость с последующей индексацией в Qdrant и BM25: один и тот же список чанков используется для обоих индексов.

**Действия:** выбор метода семантического чанкинга, реализация в коде индексации (и в скрипте переиндексации по Б.4), удаление/отключение старого `enhanced_text_chunking` для БЗ (при желании оставить для других целей).

### Б.3. Язык в GenerateResponse: опциональная передача (uz/ru) и отключение автоопределения

**Цель:** дать возможность вызывающей стороне явно задать язык ответа; при переданном языке не вызывать автоопределение языка для этого запроса.

**Требования:**

1. **Сигнатура**  
   В метод (функцию) генерации ответа добавить опциональный параметр языка, например:
   - `language: Optional[str] = None` (допустимые значения `"uz"` или `"ru"`).

2. **Поведение**
   - Если `language` передан и равен `"uz"` или `"ru"`: использовать его для построения промпта и формата ответа; **не вызывать** `detect_language_openai` для этого сообщения в контексте генерации ответа.
   - Если `language` не передан (`None`): поведение как сейчас — язык определяется через текущую логику (detect_language_openai и т.д.) и передаётся в `generate_response`.

3. **Точка входа API**  
   В теле/параметрах запроса к `POST /process_message` добавить опциональное поле, например `language: Optional[str] = None`. Если клиент передал `language in ("uz", "ru")`:
   - установить контекст запроса (ContextVar) в этот язык;
   - не вызывать детекцию языка для сообщения (или вызывать только для внутренней статистики, не подставляя результат в пайплайн);
   - передать этот язык в `classify_query`, `find_relevant_context` (или новый поиск), `generate_response`.

4. **Обратная совместимость**  
   При отсутствии поля `language` в запросе — полное сохранение текущего поведения (автоопределение и передача языка в генерацию).

**Действия:** добавить параметр в функцию `generate_response`; добавить опциональное поле в `MessageRequest` и логику в `process_message`; при переданном языке не вызывать детекцию (или использовать переданный язык везде, где сейчас используется результат детекции).

### Б.4. Страница для менеджеров (FastAPI) по KB_MANAGEMENT_FEATURE.md

**Цель:** реализовать веб-страницу управления базой знаний для менеджеров колл-центра в соответствии с `docs/KB_MANAGEMENT_FEATURE.md`.

**Требования (кратко):**

1. **Эндпоинты**
   - `POST /UploadFile`: приём PDF (file, name=KB.pdf), валидация (MIME, magic bytes `%PDF`, размер ≤ 20 МБ, читаемость через pdfplumber). При наличии `kb/KB.pdf` — переименовать в `kb/KB_backup.pdf`. Сохранить загруженный файл как `kb/KB.pdf`. Обновить `kb_hash.json` (поле `upload_date`).
   - `POST /IndexDB`: проверка наличия `kb/KB.pdf`, проверка доступности Qdrant и модели эмбеддингов, lock переиндексации; создание коллекции `kb_v1_{timestamp}`, запуск индексации (PDF → семантические чанки → эмбеддинги → Qdrant + BM25), переключение alias `kb_current`, обновление BM25 в памяти, обновление `kb_index_ready`, обновление `index_date` в `kb_hash.json`, снятие lock.
   - `GET /kb/status`: возврат состояния (file_exists, file_name, file_size_mb, upload_date, index_date, index_ready, indexing_in_progress, backup_exists).

2. **Авторизация**  
   Все перечисленные эндпоинты и страница `/admin/kb` защищены HTTP Basic Auth (логин/пароль из `ADMIN_USER`, `ADMIN_PASSWORD` в `.env`; сравнение через `secrets.compare_digest`).

3. **Веб-страница `/admin/kb`**  
   Одностраничное приложение: дата последнего обновления БЗ, File Picker (PDF, макс. 20 МБ), кнопки «Загрузить файл» и «Проиндексировать базу знаний», модальные подтверждения и уведомления об успехе/ошибке; при загрузке страницы — запрос `GET /kb/status`. Обслуживание через FastAPI (StaticFiles или шаблоны).

4. **Файлы и метаданные**  
   Каталог `kb/` (KB.pdf, KB_backup.pdf); расширение `kb_hash.json` полями `upload_date`, `index_date` (и при необходимости `collection`, `uploaded_by`). Переменные `KB_MAX_FILE_SIZE_MB`, `ADMIN_USER`, `ADMIN_PASSWORD`. В `docker-compose` — volume для `kb/` (например `kb_data`).

5. **Конкурентность**  
   Один глобальный lock переиндексации; при занятом lock на `POST /IndexDB` — 409. Во время индексации бот продолжает работать со старой коллекцией через alias.

**Действия:** реализовать эндпоинты, Basic Auth, HTML/JS для `/admin/kb`, расширить `kb_hash.json`, добавить volume и переменные окружения; добавить `python-multipart` в зависимости.

### Б.5. Сохранение контекста чата и асинхронное переписывание контекста

**Цель:** обеспечить, чтобы бот не терял контекст диалога и стабильно учитывал его при генерации ответов. Контекст хранить и при необходимости переписывать (суммаризировать/сжимать) асинхронно, чтобы умещаться в лимиты модели и оставаться релевантным.

**Требования:**

1. **Хранение контекста чата**
   - Помимо короткой истории сообщений (`chat:*:history`, последние N реплик) хранить **расширенный контекст диалога** для каждого `chat_id`: суммаризованное или структурированное представление предыдущих обменов (тема, ключевые факты, решения), чтобы бот учитывал их при ответе.
   - Хранилище: Redis (например ключи `chat:{chat_id}:context` и при необходимости `chat:{chat_id}:context_updated_at`). При длинных диалогах — ограничение размера или TTL по политике сессии.

2. **Учёт контекста при генерации**
   - В `generate_response` (или аналог) передавать не только сырую историю `history` (последние 2–3 реплики), но и **сохранённый контекст чата** (краткое изложение или структурированный контекст).
   - В системный/пользовательский промпт включать: «Контекст диалога: …» и/или «Предыдущие реплики: …», чтобы модель давала ответы с учётом всей беседы (уточнения, отказы, уже данная информация).

3. **Асинхронное переписывание контекста**
   - После успешной генерации ответа (или после логирования взаимодействия) **асинхронно** запускать задачу обновления контекста чата:
     - Вход: текущий сохранённый контекст (или пусто), последние сообщение пользователя и ответ бота (и при необходимости последние реплики из `history`).
     - Действие: вызов LLM (лёгкая модель, например gpt-4o-mini) для обновления контекста: «Обнови краткое изложение диалога с учётом нового обмена: пользователь сказал …, бот ответил …» или «Добавь к контексту ключевые факты из этого обмена».
     - Результат сохранять в Redis (`chat:{chat_id}:context`). Выполнение в фоне, без блокировки ответа клиенту.
   - Ограничения: не более одной фоновой задачи обновления контекста на чат в момент времени (очередь или lock по `chat_id`), таймаут и retry при ошибке LLM, при сбое — оставлять старый контекст или откатываться к последним N сырым репликам.

4. **Инициализация и инвалидация**
   - При первом сообщении в чате контекст пустой; при долгой неактивности (например по истечении сессии или TTL) контекст можно сбрасывать или оставлять до следующего `cleanup_inactive_sessions`.
   - При эскалации (передача оператору) контекст можно сохранить для последующего использования или очистить — по продуктовой логике.

5. **Конфигурация**
   - Вынести в конфиг/env: включение/выключение асинхронного переписывания контекста, максимальный размер контекста (символы/токены), модель и параметры для переписывания, TTL контекста в Redis.

**Действия:** спроектировать формат хранения контекста (текст суммаризации или JSON с полями); реализовать сервис обновления контекста (например `app/services/context.py`: `get_chat_context`, `update_chat_context_async`); в пайплайн после ответа — ставить в очередь фоновое обновление контекста; в `generate_response` подставлять сохранённый контекст в промпт; при модулизации (Б.6) включить этот сервис в структуру.

### Б.6. Разделение bot9b на модули

**Цель:** вынести логику из одного файла `bot9b.py` в отдельные модули для читаемости, тестирования и поддержки.

**Предлагаемая структура (см. также Б.7):**

- **`app/main.py`** — создание FastAPI-приложения, подключение роутеров, lifespan (инициализация БД, Redis, загрузка БЗ, запуск фоновых задач, Prometheus).
- **`app/api/`** — эндпоинты:
  - `process.py` — `POST /process_message`, `POST /escalate`;
  - `health.py` — `GET /health`, `GET /stats`;
  - `synonyms.py` — `GET /synonyms/reload`, `GET /synonyms/status`;
  - `language.py` — `GET /language_detection_stats`, `POST /clear_language_cache`;

  - `language.py` — детекция языка (OpenAI, кэш, last_language);
  - `embeddings.py` — получение эмбеддингов (OpenAI/другая модель), кэш Redis;

  - `search.py` — гибридный поиск (Qdrant + BM25 + реранкер);
  - `classification.py` — классификация запросов (локальные правила + OpenAI);

- **`app/models/`** — Pydantic-модели запросов/ответов.
- **`app/utils/`** — синонимы (загрузка, нормализация), Redis-safe обёртки, метрики Prometheus (или вынести в `app/monitoring/`).

**Действия:** поэтапно выносить функции в соответствующие модули, импортировать в `main.py` и роутерах; сохранить единую точку входа `uvicorn app.main:app` (или оставить алиас `bot9b:app` через re-export).

**Новый пайплайн обработки сообщения:**

1. Вход: `POST /process_message` (опционально `language: "uz" | "ru"`).
2. Если передан `language` → установить в ContextVar, не вызывать детекцию; иначе — `detect_language_openai` (как сейчас).
3. Анонимизация, проверка PII-only — без изменений.
4. Redis: сессия, история, эмбеддинг последнего сообщения, счётчики — без изменений.
5. **Контекст чата:** прочитать сохранённый контекст диалога из Redis (`chat:{chat_id}:context`); при отсутствии — пустая строка или последние реплики из истории.
6. Эмбеддинг запроса (модель по конфигу: OpenAI или BGE-M3 для Qdrant).
7. Детекция повтора, классификация, логика эскалации — без изменений. **При эскалации** — ответ клиенту («передаём оператору» / «звоните») и возврат; шаги 8–11 не выполняются.
8. **Поиск контекста (RAG)** (только если не эскалация): гибридный поиск:
   - векторный поиск в Qdrant по эмбеддингу запроса (top_k, например 20);
   - BM25 по тексту запроса (top_k);
   - объединение кандидатов по id чанка;
   - реранкер (uz/ru) по парам (запрос, чанк) → топ 3–5 чанков.
9. **Генерация ответа:** `generate_response(rag_context, query, history, chat_context=..., language=language)` — в промпт подставляются и RAG-чанки, и сохранённый контекст чата; опциональный явный язык.
10. Логирование и ответ клиенту.
11. **Асинхронное обновление контекста:** после ответа поставить в очередь фоновую задачу переписывания контекста чата (текущий контекст + последний обмен → LLM → сохранение в Redis); выполнение не блокирует ответ.

**Пайплайн индексации БЗ (при вызове POST /IndexDB):**

1. Lock, проверка `kb/KB.pdf`, доступность Qdrant и модели.
2. Извлечение текста из PDF (pdfplumber).
3. **Семантический чанкинг** → список чанков.
4. Эмбеддинги для чанков (batch при возможности).
5. Создание коллекции Qdrant `kb_v1_{timestamp}`, загрузка векторов и payload (текст, id).
6. Переключение alias `kb_current` на новую коллекцию.
7. Построение/обновление BM25-индекса по тем же чанкам.
8. Обновление `kb_hash.json` (index_date и т.д.), снятие lock.

**Архитектура (новая):**

- **Вход:** FastAPI (модули в `app/`), роутеры разделены по зонам (process, health, admin, ...).
- **Хранение:** PostgreSQL (interactions), Redis (кэш, сессии, **контекст чата по chat_id**), Qdrant (векторный индекс чанков), BM25 в памяти (обновляется при переиндексации).
- **Внешние сервисы:** OpenAI (или переключение эмбеддингов на BGE-M3), реранкер (multilingual/uz/ru); для асинхронного переписывания контекста — LLM (например gpt-4o-mini).
- **Админка:** страница `/admin/kb` и API загрузки/индексации с Basic Auth.
- **Фоновые задачи:** обновление контекста чата после каждого ответа (очередь по chat_id, без блокировки ответа).
- **Мониторинг:** Prometheus (порт 8001), при необходимости расширить метрики (латентность реранкера, Qdrant, очередь/задержка обновления контекста).

### Б.8. Дополнительные предложения по улучшению

1. **Эмбеддинги**  
   Учесть возможность переключения эмбеддингов через конфиг на **BGE-M3** (или другую multilingual-модель) для эмбеддингов: лучше покрытие uz/ru, возможность хранить в Qdrant без зависимости от OpenAI для эмбеддингов и снижения затрат.

2. **Конфигурируемые пороги**  
   Вынести в конфиг/env: `SIMILARITY_THRESHOLD`, `MAX_HISTORY_SIZE`, top_k для поиска и реранкера, размер чанка и overlap для семантического чанкинга — чтобы подстраивать без правок кода.

3. **Таймауты и retry**  
   Явные таймауты и политики retry для Qdrant, реранкера и OpenAI; при недоступности реранкера — fallback на объединённый список без реранкинга (или только векторный топ).

4. **Метрики**  
   Добавить метрики: время гибридного поиска (vector, BM25, rerank), количество кандидатов до/после реранкинга, ошибки Qdrant/реранкера — для мониторинга и тюнинга.

5. **Тесты**  
   Юнит-тесты для семантического чанкинга, гибридного поиска (mock Qdrant/BM25), логики языка в `generate_response` и эндпоинтов админки (с mock auth).

6. **Версионирование API**  
   При добавлении полей (например `language`) сохранить обратную совместимость; при будущих breaking changes рассмотреть префикс версии (`/v1/process_message`).

7. **Лимиты и защита**  
   Rate limit по `chat_id` или IP для `/process_message`, ограничение длины `message` и размера `history` на входе — для защиты от злоупотреблений.

8. **Логирование и трейсинг**  
   Единый request_id (или trace_id) по цепочке: приём запроса → поиск → генерация → ответ; логировать его во всех ключевых шагах для разбора инцидентов.

9. **Анализатор (analyzer.py)**  
   При желании перенести в `app/scripts` или оставить отдельным скриптом, но использовать общие модели классификации (например, вынести схему категорий в общий модуль) для согласованности с ботом.

10. **Документация**  
    Обновить README: новая архитектура, переменные окружения (Qdrant, ADMIN_*, реранкер), описание опционального параметра `language` в API и страницы `/admin/kb`.

## Недочёты и уточнения ТЗ

Ниже перечислены выявленные пробелы и рекомендации по уточнению ТЗ перед реализацией.

1. **Путь к файлу БЗ**  
   В текущем коде используется `KB.pdf` в корне проекта; в `KB_MANAGEMENT_FEATURE.md` и в ТЗ (Б.4) — каталог `kb/` и файл `kb/KB.pdf`. В ТЗ следует **явно зафиксировать**: после внедрения админки единственный источник БЗ — `kb/KB.pdf`; при старте приложения загрузка/проверка кэша выполняется из `kb/KB.pdf`; при отсутствии файла — поведение как сейчас (ошибка или fallback) описать отдельно.

2. **Qdrant: размещение и конфигурация**  
   В Б.1 не указано, где и как поднимать Qdrant (локально, Docker, облако). Рекомендуется добавить: включение сервиса Qdrant в `docker-compose.yml` (образ, порт 6333), переменные окружения `QDRANT_HOST`, `QDRANT_PORT` (или `QDRANT_URL`), использование их при инициализации клиента и в пайплайне индексации.

3. **Контекст чата и очистка сессий**  
   В Б.5 описано хранение контекста в Redis и инвалидация «по политике сессии», но не зафиксировано, нужно ли **удалять** ключи `chat:{chat_id}:context` (и при необходимости `context_updated_at`) в рамках существующей задачи `cleanup_inactive_sessions` при истечении сессии. Рекомендация: явно указать в ТЗ — при очистке неактивной сессии (таймаут 1 ч) контекст чата также сбрасывать (delete ключей контекста), чтобы не накапливать данные и не использовать устаревший контекст при новом заходе пользователя.

4. **Пайплайн индексации и глобальное состояние**  
   В Б.7 в пайплайне индексации не упомянуты: (а) обновление флага **`kb_index_ready`** (или аналога) после успешного переключения alias и обновления BM25; (б) откуда бот берёт **список чанков** для BM25 после переиндексации (in-memory глобальная переменная/сервис, обновляемая в том же процессе после POST /IndexDB). Стоит добавить в Б.4/Б.7 явные шаги: по завершении индексации выставить `kb_index_ready = True` и обновить in-memory список чанков (и BM25-индекс), от которого зависит поиск до следующей переиндексации.

5. **Совместимость загрузки БЗ при старте и админки**  
   Сейчас при старте вызывается `load_knowledge_base()` из `KB.pdf`. После введения `kb/KB.pdf` и POST /IndexDB нужно определить: при старте приложения при отсутствии `kb/KB.pdf` не пытаться индексировать или показывать «БЗ не готова»; при наличии файла и актуального кэша Qdrant/BM25 — загружать индекс из Qdrant (alias `kb_current`) и поднимать BM25 из сохранённых чанков (или из Qdrant payload). ТЗ лучше дополнить явным сценарием «старт приложения при уже проиндексированной БЗ» (чтение alias, загрузка чанков для BM25 из хранилища).

6. **Реранкер: выбор модели и fallback**  
   В Б.1 указано «лёгкий реранкер, понимающий uz/ru», но не заданы критерии выбора (self-hosted vs API, лимит задержки в мс). В Б.8 есть fallback при недоступности реранкера — в Б.1 полезно явно указать: при недоступности реранкера использовать объединённый список кандидатов без реранкинга (или только векторный топ) и логировать событие.

7. **Формат и лимиты контекста чата**  
   В Б.5 описан «суммаризованный или структурированный контекст», но не заданы: максимальный размер в символах/токенах при записи в Redis и при подстановке в промпт, а также поведение при превышении (обрезание, новая суммаризация). Рекомендация: зафиксировать в ТЗ лимит (например 500–1000 токенов) и правило обрезки/перезаписи.

8. **Очередь фоновых задач контекста**  
   В Б.5 и Б.7 упомянуты «очередь» и «не более одной задачи на чат», но не указан способ реализации (in-memory очередь по chat_id, Redis lock, отдельный воркер). Для однопроцессного приложения достаточно in-memory словаря «chat_id → asyncio.Task» или очереди с дедупликацией по chat_id; при масштабировании может понадобиться Redis-based очередь. Имеет смысл в ТЗ кратко указать вариант для первой версии (in-process, lock/очередь по chat_id).

9. **Нумерация и перекрёстные ссылки**  
   Проверить все ссылки между пунктами (Б.1 → «обновление индексации в ТЗ п. Б.4», Б.5 → «при модулизации (Б.6)») — они актуальны. В резюме и вводной фразе указано «пункты 1–7»; по факту пунктов изменений семь (Б.1–Б.7), Б.8 — предложения; формулировка корректна.
